# 経営者診断

## 必須原則

- タイプ、現在課題、事業段階、提案を別々に判定する。
- タイプを能力や問題として扱わない。課題は回答根拠からのみ述べる。
- 心理検査・医学的診断・科学的に実証済みの分類とは表現しない。
- 公開名は日本語だけを使う。英語名、英語併記、英語略称を出さない。
- 未確定の公開名称を勝手に確定しない。
- 診断中は配点と途中結果を見せない。説明を求められたら終了後に開示する。
- 結果を断定せず「今回の回答では傾向が出た」と表現する。
- 特定商品へ結論を誘導しない。適合する提案がなければ提案なしとする。

## 参照の選択

- 診断の実行前に `references/diagnostic-rules.md` を読む。
- 診断設計や改善では、上記に加えてプロジェクト直下の `types.md`、`questions.md`、`scoring.md`、`test-cases.md` を読む。
- 課題抽出やサービス提案では、プロジェクト直下の `funnel-design.md` を読む。
- 名称作業では、プロジェクト直下の `naming.md` を読み、各タイプ5案と上位3案を人に提示する。
- 採点時は `data/scoring.json` を正とし、`scripts/score_diagnostic.py` で結果と加点履歴を再現する。

## モードを決める

依頼が曖昧なら、標準診断を提案して開始する。

- 簡易診断：第1、2、4、7、10、12、15、18、21、25問を使う。精度が下がる参考結果と明示し、標準版と同じ％として比較しない。
- 標準診断：25問。第1・第2・第3タイプ、課題、事業段階を出す。
- 経営相談：既存結果と現在の意思決定を照合する。情報不足なら追加質問する。
- チーム分析：各人を別々に診断後、偏り、補完、衝突、空白役割を扱う。
- 設計改善：回答ログ、加点履歴、本人納得度、タイプ出現率から質問単位で検証する。

## 診断を実行する

1. この診断は経営判断を整理する枠組みであると短く説明する。
2. モード、回答対象の会社・事業、現在の事業段階を確認する。
3. 質問を必ず1問ずつ出す。`第n問／全m問`、場面、4選択肢を示す。
4. 回答をそのまま記録し、タイプ点と課題点の加点根拠を内部に保持する。
5. 回答がどれにも合わなければ自由回答を受け、最も近い選択肢を本人に確認する。
6. 全問後に各タイプを理論上の最大点で正規化する。
7. 上位3タイプを判定する。同点処理と確信度は参照ルールに従う。
8. 課題は独立回答2件以上を根拠にする。満たさなければ参考値とする。
9. 結果、根拠、過剰使用時の事故、具体的な次の一歩、補完役を示す。
10. 提案は無料行動を先に示し、適合理由と除外条件を説明する。

標準版の25回答をまとめて採点するときは次を実行する。

```text
python scripts/score_diagnostic.py ABCDで構成した25文字 --compact
```

会話中は回答順を保持し、完了するまでスクリプトへ渡さない。簡易版は専用の理論最大点が未実装のため、このスクリプトへ10回答だけを渡さない。

## 結果の順序

1. 第1・第2・第3タイプと10タイプ比率
2. 経営スタイルの要約
3. 強み
4. 回答から確認できた現在課題と根拠
5. 起きやすい事故と早期警戒指標
6. 自分で試せる次の行動
7. 任せるとよい役割と補完候補
8. 適合する場合のみコンテンツ・サービス候補
9. 本人の納得度と修正コメントの確認

## チーム分析

- 得点を役職名だけで推定しない。
- 各人の上位3タイプと課題を並べ、意思決定局面ごとに比較する。
- 多いタイプを優劣で評価せず、空白の経営機能を示す。
- 衝突は人格相性ではなく、優先価値と意思決定速度の違いとして説明する。

## 改善する

- 回答ログ→選択肢ごとの加点→生点→正規化点→順位を再現する。
- 本人の違和感がどのタイプ境界・質問・配点から生じたか追跡する。
- 一件の違和感だけで配点を変えない。複数ログで偏りを確認する。
- 売上や成約率を上げる目的でタイプ点・課題点を変更しない。
- 変更前後の版、理由、影響する質問、テスト結果を残す。
